Waterfall to Kanban: Make the Waiting Visible

Waterfall rarely fails because people sequence their work. It fails because nobody can see the queues between the stages. Kanban fixes that by starting with the process you already run — not by throwing it out on day one.
Visualize. Flow. Measure. Improve.

Start with what the team does now. The fastest way to lose a waterfall team is to tell them everything they know is wrong. The fastest way to win them is to put their own process on a board and let them see where the work actually waits.

Where this comes from. The transition method is how I coach teams off waterfall. The transition, in five moves

  1. Map the existing processMirror the current sequential handoffs on one shared board — a wall for a team in one room, a digital board for a remote or hybrid one — using the stage names the team already uses — Requirements, Architecture Review, Development, QA, Deployment. Split each stage into In Progress and Done so the queue build-up and the waiting time show up on their own.
  2. Establish WIP limits graduallySet the first limits to match current headcount or historical capacity, so nobody’s week changes overnight. Then tighten them a little at a time. Each notch surfaces the next downstream bottleneck and rewards finishing work over starting it.
  3. Shift standups to focus on flowWalk the board from right to left — closest to done first — in the room or with the board shared on camera. The conversation is about unblocking what is stuck and finishing what is close, not a round of individual status reports.
  4. Measure flow metricsTrack cycle time, lead time, throughput and a cumulative flow diagram. Real numbers replace estimation-by-opinion and give the retrospective something to inspect.
  5. Formalize the pull system and explicit policiesGive every column an entry and exit rule — a Definition of Ready and a Definition of Done per stage — so people pull work only when they have capacity.
“Don’t tear the process down. Put it on the wall, and let the team see where the work waits.”
Fewer handoffs. More flow.

Where AI earns its place

AI doesn’t run the transition. It takes the reading and drafting off the team’s plate so the conversations happen sooner and rest on evidence.

Requirements decomposition

Read legacy requirements documents and architecture specs and draft small, vertical-slice stories with first-pass acceptance criteria for the team to refine.

Historical workflow discovery

Analyze past tickets and repository history to find the hidden queues, the handoff delays and the real cycle times of the legacy stages.

Probabilistic forecasting

Replace the static Gantt estimate with Monte Carlo simulations over actual delivery history — dates with a confidence range instead of a single hopeful number.

Proactive bottleneck alerts

Monitor the tracking tool and flag aging work items that are drifting past normal cycle time, before they breach a service level.

Drafting explicit policies

Draft the Definition of Ready, Definition of Done and class-of-service policies from the organization’s own governance standards — for the team to edit and own.

The rule underneath

A person reviews every AI output before it lands on the board, and no client data goes into public AI tools — enterprise-governed tooling only.

The data connection — AT&T, then and now

At AT&T I led the Scrum team through a major data migration that sunset a legacy platform. I was the central gateway for access — coordinating across teams to map the data, request the clearances, and make sure every handoff was secure. Then I managed the final decommissioning of the old platform’s services, working through compatibility issues so the cutover landed without disrupting the business.

  • Data mapping and discovery — early discovery to map legacy source fields and structures accurately to the target platform.
  • Access control and gateway coordination — the single point of contact across siloed cross-functional groups, securing clearances for the tables, databases and environments the migration needed.
  • Legacy compatibility remediation — finding the components that needed updates before cutover could happen safely, and getting them fixed first.
  • Decommissioning and cutover verification — orchestrating the shutdown and sunset of the legacy services once end-to-end transfer was validated.

That project taught me where a data migration breaks. The research behind the agent is how I’d stop it breaking today:

Adapting it for data engineering

Data teams inherit the hardest version of waterfall: one giant pipeline, one big release, and breakages that show up downstream days later. The same moves apply, with four adaptations.

  1. Map pipeline lineage and dependenciesBreak monolithic pipelines into modular data-delivery slices. Use SQL, dbt lineage graphs and data catalogs to link upstream schema changes and transformation prerequisites as visible blockers on the board.
  2. Automate data quality gatesBuild validation suites — Great Expectations, dbt tests — into each card’s exit criteria, so automated verification is part of the Definition of Done rather than a step after it.
  3. Alert on schema drift upstreamMonitor source systems and DDL logs. When an unexpected schema change lands, raise an Expedite card automatically, pre-filled with the impact analysis.
  4. Decompose monolithic ETL / ELT jobsBreak legacy stored procedures and orchestration scripts into incremental micro-batch stories or modular pipeline stages that can be pulled one at a time.

The flow math

MetricWhat it measuresFormula
Lead timeFrom the moment a request is made or committed to the backlog until the value reaches the customer.Completion − Request
Cycle timeFrom when active work starts — pulled into In Progress — until it reaches Done.End − Start
ThroughputCompleted items delivered per unit of time, such as per week or per sprint.TH = N ÷ T
Little’s LawHow work in progress, throughput and average cycle time relate in a stable system.WIP = TH × Cycle time
Why Little’s Law matters in practice: rearranged, it says average cycle time equals WIP divided by throughput. If the team can’t finish faster, it can still deliver sooner — by starting less at once. That is the whole argument for WIP limits in one line.
